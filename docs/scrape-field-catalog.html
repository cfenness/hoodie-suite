Uber Eats

mac headful browserdailylive landingchannel aggregator markup
Lands to ubereats_products

Our own real Chromium on the Mac's residential IP (no Bright Data, no manual cookie) loads the Uber first-party BFF www.ubereats.com/_p/api/*. A persistent profile keeps the delivery zone sticky. Because the retailer marks items up on the aggregator to cover the platform fee, every record carries channel=ubereats — paired with the retailer's direct price it yields the effective take-rate.

Levels of pull

  1. 1Zone feed (getFeedV1)
    GET /feed?diningMode=DELIVERY&pl=<base64 location>
    Merchant discovery. Yields slug, store uuid, merchant name, storefront href from the /store/<slug>/<uuid> links, infinite-scrolled to load every merchant. Filtered to alcohol/grocery retailers.
  2. 2Store catalog (getStoreV1)
    fires on trusted click-through into a store
    The item list (lighter). Title + price live in flat keys; list price, promo tag/uuid, the “SIZE • X% ABV” descriptor, and the stock-bucket label live in nested rich-text + overlay tags. No UPC / no quantity at this level.
  3. 3Item detail (getMenuItemV1)
    POST /_p/api/getMenuItemV1 (replayed per item)
    The richest schema — see the callout below. Adds the UPC/GTINs, full promo mechanics, the availability/quantity layer (maxPermittedNumber), unit/measure, and every attribute. We learn the app's real request from one click, then replay it per item (~3/s) to upgrade the whole catalog.
What is getMenuItemV1? It's Uber Eats' per-item detail endpoint — the call the app fires when you tap a product tile. It returns the single richest view of one item: identity + productIdentifiers[] (the GTIN/UPC), itemPromotionV2 (promo %/flat/uuid), the purchaseInfo.purchaseOptions[].quantityConstraintsV2 block whose maxPermittedNumber is min(on-hand, purchase-limit) — our closest read on real inventory — plus unit/measure, dietary labels, and media. getStoreV1 (the catalog list) is a lighter subset of the same fields with no barcode or quantity, so we capture one real getMenuItemV1 request per store and replay it item-by-item to enrich everything. parse_item() targets this schema.

Lands to postmates_products

Postmates runs on the same Uber BFF as Uber Eats — identical getStoreV1 / getMenuItemV1 schemas. The only difference is the domain (postmates.com) and feed base; the same base64 zone works on both. The entire recipe, parser and field set are reused; records just land to a separate channel table.

Levels of pull

  1. 1Zone feed
    GET postmates.com/feed?diningMode=DELIVERY&pl=<base64 location>
    Same as Uber Eats level 1 — merchant slug/uuid/name/href.
  2. 2Store catalog (getStoreV1)
    same schema as Uber Eats
    Same catalog shape — title, price, list price, promo, descriptor, stock label.
  3. 3Item detail (getMenuItemV1)
    same schema as Uber Eats
    Same rich detail — UPC/GTINs, promo mechanics, quantity layer, attributes, media.

Instacart

recon not yet landingmac BD Browseralcohol-gated needs age-verified login
Lands to (not landing yet)

Status: cracked, but not reliably landing data yet. Instacart forbids scraping and is DataDome / Forter protected. Two routes are built. (A) the site's own persisted GraphQL SearchResultsPlacements op driven through a Bright Data Browser session — the API and anti-bot are solved, but the last mile (session automation) isn't hardened. Alcohol needs a logged-in, age-verified session (anonymous returns “alcohol isn't available”). (B) Bright Data's managed Instacart dataset (paid, ToS-gray), whose exact field names vary by dataset — the connector self-reports degraded and dumps the first batch to lock the mapping.

Levels of pull

  1. 1Open session + set zone
    bdata browser open https://www.instacart.com/ --country us
    A delivery zone auto-sets from the residential IP; the homepage lists real retailers.
  2. 2Enter a store, capture zone params
    click a non-membership grocery → read {shopId, postalCode, zoneId}
    Storefront context (shopId) + zone (postalCode, zoneId) scraped from a live SearchResultsPlacements request URL.
  3. 3Search → items
    GET /graphql?operationName=SearchResultsPlacements&variables={query,shopId,zoneId,…}
    Clean JSON at data.searchResultsPlacements.placements[] → Item* nodes → name, price viewSection, size, image (see field table).
Why Instacart isn't in the daily registry: the product API and anti-bot are proven, but membership walls, the enter-store-first requirement, per-request param scraping, and the alcohol login gate mean it doesn't yet land reliably. The fields below are what the connector is built to capture — present them to the team as the target schema, not a live feed.

Kroger

mac warmed cookiedailylive landingcounts exact on-hand
Lands to kroger_atlas_products

Kroger's internal “atlas” product API — the rich per-GTIN payload the site/app use, far deeper than the public developer API. One endpoint, batched ~20 GTINs/call, keyed by GTIN. Gated by the x-laf-object header (which carries the store) + a warmed session cookie. Returns master data, bottle dimensions, ABV, Kroger's commodity taxonomy, planogram, per-modality availability and — when the response carries populated inventory objects — an exact per-store on-hand count.

Levels of pull

  1. 1Seed the GTIN universe
    from kroger_products (public API UPC seed) or --gtins
    The list of GTIN13s to enrich (our bev-alc UPC universe by default).
  2. 2Atlas product fetch
    GET /atlas/v1/product/v2/products?filter.gtin13s=…&projections=items.full,offers.compact,nutrition.label,inventory.projected,variantGroupings.compact
    One rich product per GTIN. The projections are the sub-levels of detail: items.full (master + dimensions + ABV + taxonomy + planogram), offers.compact (price/promo), inventory.projected (per-modality level + exact on-hand), nutrition.label, variantGroupings.compact.
Auth note: the store is passed in the x-laf-object request header as [{listingKeys:[storeId], modality:{type:PICKUP, handoffLocation:{facilityId, storeId}}}] — the server reads laf[0].modality.handoffLocation.storeId. Needs KROGER_COOKIE + KROGER_STORE + KROGER_FACILITY.

Total Wine

mac PerimeterX browserdailylive landingcounts exact units + shelf
Lands to total_wine_products + retail_observations

Total Wine's own getProduct JSON API — the call its product pages use — keyed by storeId. Product universe comes from the published sitemap (/p/<productId>). Gives exact unit counts + shelf position (like ABC, but with the physical bay). PerimeterX binds the cookie to the IP, so warm + pull share one IP (TW_FETCH=direct = $0 local warm; bdbrowser = through a BD Browser session).

Levels of pull

  1. 1Product universe (sitemap)
    GET /sitemap → /p/<productId> → skuId “<productId>-1”
    Every product URL (each size variant is its own /p/ URL). robots-allowed; /search/ is never used.
  2. 2Per-store product detail (getProduct)
    GET /product/api/product/product-detail/v1/getProduct/<skuId>?shoppingMethod=INSTORE_PICKUP&state=US-<ST>&attrConfig=true&storeId=<storeId>
    The full per-store record: price, exact units on hand, ABV, physical bay/shelf/aisle, the geo categories (varietal/country/region), the finish/taste/body characteristics, reviews and awards. Lands two grains — a dated per-store observation (with qty) + a total_wine_products catalog enrichment row.
No UPC: Total Wine's getProduct carries no barcode field — upc stays empty by design. Identity is the skuId + brand/name/size/geo.

ABC Fine Wine & Spirits

headless stdlibdailylive landingcounts per-store on-handpolite 10s crawl-delay
Lands to retail_observations (+ abc_products)

ABC FWS (abcfws.com) runs on BigCommerce. The store is a product option — each product page lists ~133 store options and available_variant_values names the in-stock ones, so we read per-store in/out + the chain price straight from the allowed product page (no robots-disallowed AJAX). For a real unit count we call the sanctioned storefront GraphQL API (JWT embedded in the page): each store is a variant carrying inventory.aggregated.availableToSell. Polite: robots 10s crawl-delay, product pages only, honest UA; self-reports degraded if the selectors drift.

Levels of pull

  1. 1Catalog (sitemap)
    GET /xmlsitemap.php?type=products&page=N
    The whole catalog as (sku, product URL). Every product type — no category filter.
  2. 2Product page (HTML)
    GET <product URL>
    Per-store binary in/out (store = BigCommerce option, in-stock subset = available_variant_values) + the chain-level price. Fallback path.
  3. 3Storefront GraphQL (real qty)
    POST /graphql (Bearer = JWT from the page) → variants[].inventory.aggregated.availableToSell
    The actual bottle count per store + variant sku/upc/gtin/isInStock/price. Preferred path; the number the HTML omits.
ABC is an inventory tracker, not a rich catalog source — it lands the dated per-store price+in/out+qty time-series (retail_observations). Day-over-day it surfaces price moves, OOS↔restock transitions, and assortment churn.

Binny's

headless Algolia feeddailylive landingcounts per-store units

Binny's runs on Algolia (public search key, client-exposed by design). We make the same query the site's search makes; each product record carries storesPriceAndInventory — a per-store array with a numeric unit count (purchaseAvailability) and per-store prices. So we get store-level price + inventory, and the day-over-day Δ of units ≈ directional units sold. No scraping, no Bright Data.

Levels of pull

  1. 1Algolia query (paginated)
    POST https://<appId>-dsn.algolia.net/1/indexes/Products_Production/query (1000 hits/page, ~31k products)

    each hit's storesPriceAndInventory[] → cell keyed sku|storeCode
    … exploded into one cell per (product, store) carrying per-store price + exact units on hand. Lands binnys_products (keyed sku+store) + the dated observation series.

Spec's

headless stdlibdailylive landingcounts per-store units
Lands to specs_products + retail_observations

Spec's (specsonline.com) serves bots (200) and embeds a per-store variants object right in the product page — ~190 store variants, each with inStock + unitPrice, so per-store price + in/out comes in one fetch. The actual unit count is one hop away: the PDP calls /api/products/stock/<store>-<upc>/ → {available:N, tracked}. So Spec's is a real counts source, not just in/out.

Levels of pull

  1. 1Catalog (sitemap)
    GET /sitemap.xml → product child sitemaps (~41k products across 21 sitemaps)
    Every product as (slug, URL).
  2. 2Product page (PDP)
    GET <product URL>
    The full product detail (type/brand/abv/region/varietal/vintage/tasting notes/pairs-with + ld+json name/description/price/image + UPC parsed from the image filename) and the embedded per-store variants block (store, sku, inStock, unitPrice).
  3. 3Inventory API (unit count)
    GET /api/products/stock/<storeCode>-<upc>/ → {status, available:N, tracked}
    The numeric units on hand per (in-stock store, product) — the count the variants block omits. Fanned out one call per in-stock store.
